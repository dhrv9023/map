Progressive System Design Interview Preparation

Structured Whiteboard Derivations • Never Memorize Diagrams
🎯 The 4-Step Whiteboard Framework:
1. Scope & Clarify (5 min): Functional requirements, non-functional requirements, traffic scale (QPS, throughput, latency SLOs, model size).
2. Capacity Estimation (5 min): Memory bounds, parameter size, KV-cache footprint, bandwidth saturation, node counts.
3. High-Level Architecture (15 min): Ingestion, API gateway, scheduler, compute/inference layer, storage, caching.
4. Deep Dive, Failure Modes & Bottlenecks (15 min): Straggler GPUs, OOM fragmentation, network partition recovery, rate limiting.

Level 1 • Distributed Systems Prerequisite Questions

Foundational Building Blocks
1. Design a Distributed Rate Limiter
Why AI Infra cares: LLM APIs (like OpenAI / Anthropic) enforce strict token-per-minute (TPM) and request-per-minute (RPM) quotas per customer tier.
Architecture: Redis Token Bucket with sliding window log; Lua script atomic execution prevents race conditions across multi-instance API gateways; graceful 429 response with Retry-After headers.
2. Design a Distributed Key-Value Cache
Why AI Infra cares: Foundation for feature caching, model metadata, and prefix KV-cache block index tables.
Architecture: Consistent hashing with virtual nodes to avoid rehashing churn; LRU eviction with doubly-linked list + hash map; read-through cache with connection pooling.

Level 2 • ML Platform & Data Pipeline Questions

Machine Learning Systems
3. Design a Real-Time Model Serving API
Requirements: 1,000 QPS, P99 latency < 50ms, model size 500MB.
Architecture: Client → Load Balancer → Stateless FastAPI Pods → Model warm-up on startup → Dynamic batcher queues requests for 5ms → PyTorch inference worker → Prometheus histogram metrics.
4. Design a Low-Latency Feature Store
Requirements: Dual storage for training (offline batch) and real-time inference (online single-digit ms lookup).
Architecture: Dual-tier: Redis for online low-latency entity lookups (<5ms) + Parquet/S3 for offline training batches; Kafka streaming updates processed via Flink to maintain training-serving consistency.

Level 3 • Core AI Infrastructure & LLM Systems (Staff Level)

Tier-1 Company Questions (NVIDIA, Meta, OpenAI, Anthropic)
Flagship Interview Question

Design a Multi-Tenant High-Throughput LLM Inference API Platform

500 QPS • Llama-3-70B • TTFT < 200ms
1. Requirements & SLA:
• Model: Llama-3-70B (FP16: 140 GB weights, FP8: 70 GB weights).
• Workload: 500 QPS; average prompt = 1,000 tokens; average output = 200 tokens.
• SLO: Time-To-First-Token (TTFT) < 200ms; Inter-Token Latency (ITL) < 25ms.
2. Capacity & Hardware Estimation:
• Weights Memory: 70B in FP8 = 70 GB → Fits on a single 80GB H100 GPU for weights, but requires multi-GPU (Tensor Parallelism TP=4 or TP=8) to provide memory bandwidth for 500 concurrent decode streams.
• KV-Cache Memory: At 1,200 total tokens per request, each sequence requires: $$\text{Mem} = 2 \times 2 \times 80\text{ layers} \times 8\text{ KV heads} \times 128\text{ head dim} \times 1\text{ byte (FP8)} \times 1200\text{ tokens} \approx 393\text{ MB per stream}$$ For 500 concurrent streams: $500 \times 393\text{ MB} \approx 196.5\text{ GB}$ purely for KV-Cache!
• Node Sizing: Provision clusters of 8×H100 SXM5 nodes running vLLM or SGLang with Tensor Parallelism TP=4 (2 model instances per 8-GPU node).
3. Architectural Flow: 
[Clients (HTTP/gRPC Streaming)]
   │
[API Gateway] → Authenticate API Key, Rate Limit (Token Bucket per tenant)
   │
[Load Balancer with KV-Cache Prefix Affinity (SGLang RadixTree Hash)]
   │
[Inference Node: 8x H100 SXM5]
   ┌── [Continuous Batching Scheduler] (Iteration-level prefill & decode interleaving)
   ┌── [PagedAttention Memory Manager] (Virtual block tables in HBM eliminate external fragmentation)
   ┌── [4-way Tensor Parallelism over NVLink (900 GB/s interconnect)]
   └── [Server-Sent Events (SSE) Streaming Engine] → Yields tokens back to client
4. Critical Bottlenecks & Failure Modes Handled:
• Client Disconnects: When a user closes the browser mid-generation, gateway detects broken TCP pipe and sends cancellation signal to vLLM scheduler, immediately freeing the KV-cache blocks rather than wasting 200 compute steps.
• Prefix Cache Sharing: System prompts (e.g. 800-token legal context) are shared across multiple requests using RadixAttention prefix caching, reducing prefill computation by 80%.
• Chunked Prefill: Prevents massive 8,000-token prompt requests from stalling ongoing single-token decode streams.
