The 7 Progressive Engineering Projects

From Single-Process API to Full-Stack AI Inference Platform
🏗️ The Architectural Lineage: Every project builds directly on the previous one. You do not build random throwaway scripts. Project 1 becomes the core engine of Project 2; Project 2's worker pool connects to Project 5's model registry; and everything culminates in Project 7's production platform.
Project 1 • Foundations

Production-Grade ML Inference Microservice

FastAPI • Docker • Pydantic • PyTest

Problem Statement: Deploying an ML model directly inside a web server without proper validation, async non-blocking execution, or health probes causes worker thread starvation and opaque server crashes under burst load.

Architecture & Features: 
Client → [NGINX Reverse Proxy] → [FastAPI Uvicorn (4 Workers)]
  • /v1/predict (Pydantic schema validation & tensor serialization)
  • /health/live (Process liveness check)
  • /health/ready (Model weights loaded in memory assertion)
  • Structured JSON logging with request_id & latency_ms timer
Resume Bullet Ready:

"Architected a production-ready ML inference microservice in FastAPI and Docker; implemented startup readiness probes and asynchronous non-blocking handlers, achieving P95 latency of <18ms under 250 concurrent requests."

Project 2 • Distributed Concurrency

Asynchronous Inference Pipeline with Queue & Worker Pool

Redis • Celery/RQ • Idempotency • Polling

Problem Statement: Heavy models (like speech-to-text or image generation) take seconds to run. Keeping HTTP client connections open causes gateway timeouts (504 Gateway Timeout). The system must be decoupled into an asynchronous job queue.

Architecture & Features: 
Client → POST /jobs → [API Gateway] → Push Job to [Redis Queue]
  • Returns HTTP 202 Accepted with { job_id: "uuid-v4" }
  • [Worker Pool (3 processes)] consumes from Redis queue
  • Idempotency key checked in Redis to prevent duplicate compute
  • Exponential backoff retries with dead-letter queue (DLQ)
Client polls → GET /jobs/{id} → Returns PENDING | RUNNING | COMPLETED
Failure Handling Handled:

What happens when a worker crashes mid-inference? Using Redis visibility timeouts (or ACK confirmation), unacknowledged jobs automatically requeue. Client duplicate submissions with the same idempotency key return cached results without re-triggering inference.

Project 3 • Performance Engineering

Dynamic Batching & Model Serving Benchmark Lab

Locust • Dynamic Batching • P99 Profiling

Problem Statement: Running individual inference requests one-by-one underutilizes GPU Tensor Cores. Grouping requests into dynamic micro-batches increases overall throughput by 4x, but adds queueing delay to the first request. How do you find the sweet spot?

Implementation Highlights: 
Implement a Dynamic Batcher with a Queue Collector:
  • Condition A: Batch size reaches max_batch_size = 16
  • Condition B: Timeout reaches max_delay_ms = 10ms
Run automated load test using Locust across concurrency 1, 10, 50, 200:
  • Plot Throughput (RPS) vs P99 Latency curve (The Knee of the Curve)
  • Measure CPU vs GPU memory footprint and queue waiting time
Measurable Results:

"Engineered dynamic batching scheduler with 10ms latency cutoff; achieved 3.8x throughput increase (from 62 RPS to 238 RPS) while maintaining P99 latency within 45ms SLO."

Project 4 • Distributed Systems

Fault-Tolerant Distributed Cluster Simulator

Python Multi-Process • Raft Basics • Heartbeats

Problem Statement: Simulates a real distributed compute cluster on your laptop without expensive cloud infrastructure. Teaches split-brain detection, leader election, and resilient state replication. 

Components implemented in pure Python multi-processing:
  1. Cluster Coordinator (Leader): Receives job requests, partitions tasks across workers.
  2. Worker Nodes (3 instances): Send periodic heartbeats every 500ms.
  3. Chaos Monkey thread: Randomly kills worker processes or drops network packets.
  4. Quorum validation: When leader misses 3 consecutive heartbeats, remaining nodes hold an election.
  5. Backpressure regulator: When pending task queue exceeds high watermark, coordinator returns HTTP 503 / backpressure signal.
Project 5 • MLOps & Platform

Mini ML Platform (Model Registry, Canary Deploy & Drift Detection)

MLflow • MinIO • Evidently AI • Canary Routing

Problem Statement: Deploying updated models directly to 100% of user traffic risks silent degradation or data drift. You need a platform to register versions, route 10% traffic to canary replicas, and detect statistical drift. 

Workflow:
  • Train baseline model & updated model; log artifacts and parameters into local MLflow + MinIO.
  • API Gateway implements weighted canary routing: 90% traffic to Model v1, 10% traffic to Model v2.
  • Background task evaluates prediction distributions using Evidently AI (Kolmogorov-Smirnov test).
  • Automated rollback trigger: If data drift or error rate exceeds threshold, router automatically switches 100% traffic back to v1.
Project 6 • LLM Systems Core

LLM Inference Architecture Lab (Laptop 4GB GPU Friendly)

vLLM / Ollama • PagedAttention • Streaming • TTFT

Problem Statement: Dissecting how high-performance LLM inference works under real physical memory constraints on your 4GB laptop GPU.

Lab Execution Plan: 
Model: Qwen-2.5-1.5B or SmolLM2 (4-bit quantized ~1.2GB VRAM)
Target: NVIDIA RTX 2050 (4GB VRAM)
Experiments run:
  1. Prefill vs Decode profiling: measure time spent in prefill (first token) vs decode (subsequent tokens).
  2. KV-Cache VRAM consumption: measure memory delta as prompt context scales from 512 to 2048 tokens.
  3. Streaming response architecture: Server-Sent Events (SSE) with cancellation handling when client aborts.
What Interviewers Care About:

Can you explain why the first token takes 80ms while tokens 2-100 take 15ms each? Can you explain what PagedAttention's block tables do when two requests share a common 500-token system prompt? This lab gives you the empirical numbers to answer with authority.

Project 7 • Capstone Production Platform

Production Multi-Tenant AI Inference & Platform Engine

Full-Stack Architecture • Docker Compose • Prometheus/Grafana

The Master Resume Capstone: Integrates API Gateway, API-Key authentication, tier-based rate limiting, dynamic model routing (Small model vs Large model), async queue fallback, and full Prometheus/Grafana observability into a single reproducible Docker Compose deployment. 

End-to-End Request Journey:
[Client] → [API Gateway (NGINX + Auth + Token Bucket)]
   ┌── If request is small/fast → [FastAPI GPU Worker Pool (Local Model)] → Immediate Stream
   ┌── If request is complex/large → Route to [Model Router / Heavy Queue] → Worker Pool
   └── Prometheus scrapes metrics → Grafana displays live TTFT, ITL, VRAM usage, and 429 rate limit counters.
