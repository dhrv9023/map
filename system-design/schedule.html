⚠️ Calibrated Schedule — Not Aspirational
The weekly plan below reflects your actual availability, not the maximum possible hours. Following a schedule you can't sustain causes burnout, not progress. Protect Mon/Wed evenings for rest and light review only.

• Tuesday: 2.5–3.0 hrs (7 PM–10:30 PM; one focused topic + implement)

🔄 Sunday 5-Question Audit & The Zero-Debt Recovery Protocol
Sunday 5:00 PM Audit (10-min written log):
1. What was actually completed? (git commits)
2. What working system was built? (runnable test/demo)
3. What can I explain independently without notes?
4. What blocked progress or caused friction?
5. What must change in next week's focus?
Strict Zero-Debt Recovery Rule:
• NEVER carry over missed hours: If you miss 8 hours, next week's budget remains 24.5 hrs, NOT 32.5 hrs.
• Shed Scope Immediately: Drop P3 Optional topics; defer secondary P1 polish; protect P0 code and tests.
• Inviolable Health Rule: Mon/Wed light review days are non-negotiable regardless of schedule slippage.

🚀 Actionable Day-by-Day Plan: The First 14 Days

Zero Passive Watching • Implementation Starts Day 1
Day 1 Foundations & Latency SLOs
Topic: Latency vs Throughput & Non-Functional Requirements.
Watch/Read: Google SRE Book, Chapter 4 (Service Level Objectives) • Martin Kleppmann Lecture 1 (Distributed Systems Introduction).
Implement: Write a Python script using time.perf_counter() that sends 100 requests to a dummy endpoint and calculates P50, P90, P95, and P99 latency percentiles.
GitHub Deliverable: Commit day01_latency_calculator.py to your repo.
Day 2 FastAPI Asynchronous Architecture
Topic: Event Loops, AsyncIO, and Worker Thread Pools.
Watch/Read: FastAPI official concurrency documentation (async def vs def).
Implement: Build a minimal FastAPI service with two endpoints: /fast (async non-blocking) and /slow (synchronous blocking CPU call). Benchmark under 50 concurrent requests with wrk or hey.
GitHub Deliverable: Commit day02_fastapi_concurrency/ with benchmark notes.
Day 3 Project 1 Kickoff: Model Packaging
Topic: Model Lifecycle, Pydantic Schema Validation & Startup Lifespan.
Implement: Create Project 1 structure. Load a small PyTorch or Scikit-Learn model during FastAPI @asynccontextmanager lifespan. Assert model weights load into memory once on startup rather than per-request.
GitHub Deliverable: Commit project1_inference_api/ with lifespan model loading.
Day 4 Dockerization & Health Probes
Topic: Docker Multi-Stage Builds, /health/live vs /health/ready.
Implement: Write an optimized multi-stage Dockerfile; add liveness and readiness probe endpoints. Ensure readiness returns HTTP 503 until model weights finish loading.
GitHub Deliverable: Commit Dockerfile and docker-compose.yml.
Day 5 Linux Profiling & Syscall Tracing
Topic: Syscalls, File Descriptors, and strace.
Implement: Run your containerized model server under load; execute strace -c -p <PID> to analyze where CPU time is spent. Log findings into an engineering report.
GitHub Deliverable: Commit day05_syscall_profiling_report.md.
Day 6 Distributed Caching & Rate Limiting
Topic: Redis Key-Value Store & Token Bucket Rate Limiting.
Implement: Add Redis to your Docker Compose. Implement a token-bucket rate limiter that restricts API keys to 20 requests per minute with atomic Lua scripts.
GitHub Deliverable: Commit rate_limiter.py with PyTest assertion suite.
Day 7 Week 1 Review & System Design Mock
Topic: Week 1 Architecture Review & System Design Practice.
Whiteboard Task: Design a Rate-Limited ML Inference API on paper/Excalidraw. Include load balancing, rate limiting, and health probes.
GitHub Deliverable: Commit architecture diagram week1_system_design.png and write a 1-page design document.

0 to 5 Evaluation & Mastery Rubric

How to Grade Yourself After Each Phase
Score Mastery Level Observed Ability Action Required
0 Unaware Cannot explain the concept or recognize the problem it solves. Cannot pass. Re-read primary documentation and watch lecture.
1 Superficial Recognizes the buzzwords (e.g. "PagedAttention", "Raft") but cannot describe mechanics. Watch the deep-dive lecture and write notes on the failure mode.
2 Guided Can explain the basic idea when prompted with diagrams or guided questions. Build the small hands-on code exercise independently.
3 Independent Can explain independently on a whiteboard and solve a standard coding exercise. Minimum Passing Grade for Stage 1.
4 Production-Ready Can implement a working multi-process solution, configure Docker/K8s, and discuss trade-offs. Ready for Junior-to-Mid AI Platform interview screens.
5 Staff-Level Can analyze edge-case failure modes, hardware bottlenecks, memory fragmentation, and defend design decisions against alternative architectures. Target for Senior / Staff AI Systems roles.
